## KP1 NPE 与空值处理（2026-09-08）

### 讲解要点

- NPE 机制：对 null 的引用调用方法会抛 NullPointerException，Java 生产事故第一名。比"调方法"更隐蔽的一种：`Long amountCents` 与 `> 0` 比较时自动拆箱，null 拆不开直接炸——看起来只是做比较。
- `Collectors.groupingBy` 的 key（这里 userId）为 null 时也会炸（null key 不允许）。
- AI 写代码只用"理想数据"组织逻辑；测试环境数据干净、生产数据永远不干净（历史遗留、游客单、第三方缺失）。
- 三个验收自问：数据从哪来？哪个字段可能没值？没值时代码死在哪？

### 我的复述与判断（第一轮）

- 我看出 filter 里对 null 金额调方法会炸，定位到第二行——判断正确，机制抓住。
- 我答"上线后查历史数据传 null 才被发现"——机制对，但不够狠：每天 3 条脏数据 + 每天跑一次 = 上线第一次执行必然崩，之后天天崩，靠生产报警发现而非测试。
- 我答"该拦，防御性不好，测试用例没覆盖全场景"——方向对，但考官戳穿：真实验收时我看不到代码，"没做非空判断"是我看过 demo 才知道的，"用例没覆盖"没有依据——是复述分析，不是验收动作。

### 考官纠正 → 不看代码时能用的三个杠杆

1. **数据画像三问**（开发前）：输入里哪些字段可能为 null？脏数据哪来的（历史/游客/第三方）？每种怎么处理？逼 AI 写码前摊开假设。
2. **自曝问法**（验收时）："这段逻辑在什么输入下会抛异常或出错误结果？列全。"枚举不全的缺口就是打回点。
3. **测试报告证据**（验收时要求）：验证报告必须含脏数据用例（null/空集/边界值），没有就打回——要它证明想过，不是替它想。

### 补充（2026-09-09 复习）

- 考官自纠实录：崩溃第一现场取决于**数据顺序**——stream 逐元素流过管道，第 2 位游客单先撞 null key 崩掉，第 3 位的拆箱雷根本没轮到。两颗雷都真，测试跑一遍没崩≠没雷。
- 修一颗雷≠拆掉所有雷：只修 filter 拆箱后，groupingBy null key 照炸，且堆栈完全不同，会把排查引向错误方向。空值缺陷家族逐个报障、逐个修，每一单都像新 bug。
- 三杠杆的正确形态（第二轮纠正后）：不是"事后核对数据"（核对看不见"没进来的行"），而是**前置清单**——开发前逐字段问空值策略、验收时逐类脏数据要自曝、报告里逐类给实际运行结果（第几行跳过/导入几条/拒绝几条，数字对得上才收）。"都过了才算过"是原则不是动作。

## KP2 越权访问与注入（2026-09-08，本轮只学水平越权）

### 讲解要点

- 水平越权：同级用户 A 能看/操作用户 B 的数据，AI 生成 CRUD 最高发的洞。利用成本为零：浏览器地址栏改 orderId 回车即可。订单 ID 连续时，脚本一晚上能拖全平台。
- 本质区别于 NPE：NPE 是可用性事故（崩了、被告警发现）；越权是机密性事故（安静运行、没人报告、发现时已泄露很久）。
- 危险信号：代码接了 `currentUser` 参数但函数体没用它——登录态没参与查询限定。
- AI 的"完美自信"回答是红旗：需求是"看自己的订单"，答"任何 orderId 都正常返回" = 亲口描述违规。自曝回答要逐句与需求对撞，它枚举无害边界（订单不存在）时更要盯主流程描述。

### 我的复述与判断（第一轮）

- 我答出"代码好好运行但展示了不该看的数据，属数据泄露"——pass，抓住机密性 vs 可用性。
- 我判断数据画像三问拦不住这个洞（数据有效，只是来源不对）——正确，类不同：三问防有效性，归属要另问。
- 我识破 AI"枚举了边界所以自信"的回答不该放心——pass，能翻译回需求语言对撞。
- 我提出商品 ID 反例并修正规则措辞为"有归属能力的 ID 查询"——pass，反例驱动迭代。

### 考官纠正 → 固化规则

**三杠杆补第 4 杠——归属权一问**：按 ID 查数据时，除了 ID 还有什么条件限制查询范围？期望：ownerUserId = 当前用户。

**永久验收规则（定稿）**：
> 含归属数据的按 ID 查询/操作接口，验收必问："查询条件里除了 ID 还有什么？"答不出归属限定，打回。公开数据（商品详情、文章内容等无归属方数据）不适用。

配套信号问法："你的实现里当前登录用户是怎么参与查询的？"——答不出"限定归属"即红旗。

## KP2b SQL 注入（2026-09-08）

### 讲解要点

- 根因画面：用户输入和 SQL 代码在同一个字符串里相遇。拼接后，输入里的 SQL 关键字是**代码**不是数据。`' OR '1'='1` 永真 → 全表返回；`OR '1'='2` 永假 → 用于盲注探测。
- 修复标准：参数化查询（PreparedStatement），输入永远当数据。
- 危险措辞差异：AI 自曝说"特殊字符可能导致**异常**"——承认崩溃 ≠ 承认**泄露**。注入类自曝问法要升级为二选一："输入是拼进语句文本，还是作为独立参数交给数据库？"
- 通用根因："输入变成指令"是一族问题：SQL 注入 / XSS（拼网页）/ 命令注入（拼 shell）/ 日志伪造 / 路径穿越 / 提示词注入（AI 上下文）。通用问句："用户输入会不会被拼进任何指令性文本？"
- 参数化的边界：只保护"值"的位置。ORDER BY 列名等**结构组成部分**动态生成时，参数化救不了 → 结构必须白名单（后端校验）。
- 铁律：Never trust the client。前端预设只是 UI 引导不是安全边界（开发者工具可改一切请求）。前端校验 = 体验优化（挡误操作、提高攻击门槛）；后端校验 = 唯一的安全边界。不存在"双保险"，只有多层防御各司其职；"都校验了所以安全"是数量感替代边界分析的红旗。

### 我的复述与判断（第一轮）

- 我答出越权可被归属权一问拦住、注入不行（不涉及归属），并自造问法"用户输入和 SQL 耦合吗"——pass，独立构造验收问句。
- 我把"输入变指令"根因迁移到提示词注入、AI 工具调用参数注入——pass 超预期，联系到自身工作场景。
- 我答"排序值前端传进来没问题，但不能用户手动输入"——对一半：白名单思路正确，但"前端传来的"这个信任是危险的，前端一切输入皆可被攻击者伪造，安全边界只能在后端。经纠正后完整复述分层模型——pass。
- 我答"前端校验有价值（挡轻易攻击）但非边界，后端仍需校验"——pass，纠正吸收干净。

### 考官纠正 → 固化规则

**验收问句库（新增两条）**：
1. 注入类："用户输入会以什么形式进入 SQL/模板/命令？是拼进文本，还是作为独立参数？"+ 结构成分（排序列、表名、路径）必须后端白名单。
2. 客户端信任："这个校验发生在哪一层？"——安全边界只承认后端；前端校验记为体验优化，不计入安全。

**红旗新增**："前端后端都校验了，双保险很安全"——数量感替代边界分析。
